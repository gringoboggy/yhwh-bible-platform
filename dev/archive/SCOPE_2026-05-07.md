# Scope update — 2026-05-07

## Vision

> "I want this to be the easiest Bible-building EPUB book system ever made.
> I'm thinking schools and all that might love it."

The product is no longer just a multi-SKU publishing pipeline for the
Ethiopian canon — it is a **white-label authoring platform** for anyone
who wants to build their own annotated Bible: schools, denominations,
small publishers, study groups, and individual scholars.

## Universal principles for every tool

1. **Fully customizable.** Every UI element, symbol, marker, kind name,
   category, color, label — assume the user will want to change it.
   Defaults exist; nothing is hard-coded.

2. **Easy.** No YAML hand-editing required. No CLI knowledge required.
   No build pipeline knowledge required. The dev tools should let a
   schoolteacher or a parish priest produce their own edition.

3. **Verifiable by book/chapter order.** Every browsing/management UI
   should default to organizing content by book → chapter → verse, so
   users can scan their own work and verify what they're including.
   Symbols, verse markers, sources, notes, attributions — all must be
   browsable in canonical reading order.

## New dev tool requested in this scope update

**Sources Navigator** — browse every note by book/chapter in canonical
order, see the source attribution for each, filter by source / kind /
book. Lets a user verify "what does this edition actually claim, and
where did each claim come from?" before they ship.

Implements μ.3 stretch in the original SPEC_MU_SYMBOL_TOGGLE.md.

## Permission granted

If empty categories (10 of 14 currently) make demos look hollow, sample
notes may be added — one per empty category — purely as reference data
so that every symbol has at least one displayable example. Mark these

## Future tools (mentioned but TBD)

The user expects more tools beyond this one. Quote: "After that maybe
we can think of some other tools to make this project impossible not
to want to buy." Listed in the comprehensive plan (dev/PLAN_2026-05-07.md).

## What this scope does NOT mean

- The Ethiopian Tewahedo edition remains the flagship. Other editions
  remain valid retail SKUs. The white-label authoring layer sits on
  top, it does not replace.
- Public-domain translation (WEB) remains the base. Adding non-PD
  translations is a separate, much bigger project.
- "Schools" is an audience, not a feature category. We're not building
  a learning management system — we're making a tool a school could use.

## Addendum (later same day) — Per-item toggles + master switches

Three more requirements added after the initial scope:

### A. Master toggle for verse-translation popups

There must be a single switch (per edition, probably) that turns ALL
verse-number translation popups on or off. When OFF:
  - Verse numbers above each verse are no longer clickable
  - The popup mechanism is fully suppressed

There is no use case for "some popups but not others" at the
translation level — it's all-or-nothing.

### B. Per-item individual toggles, organized by book/chapter

Because the by-book/chapter UI already exists (Sources Navigator, μ.3),
every individual entity must have its own on/off toggle in that UI:

  - every symbol (note) → toggle on/off
  - every cross-reference link → toggle on/off
  - every source attribution → toggle on/off
  - every verse-translation popup (when master switch is ON) → toggle on/off

Goal: a user can scroll their book in canonical order and turn off
literally any individual item they don't want, making the book
"completely customizable" at the most granular level.

### C. System-wide sync

Every tool and every UI in the system must reflect changes made
anywhere. Toggling a note off in the Sources Navigator must:
  - Update the matrix counts at /matrix immediately
  - Be reflected in the build (the EPUB output)
  - Persist across sessions
  - Not require a manual rebuild step in the user's mind

This is a cross-cutting infrastructure requirement, not a single tool.
It probably implies a "disabled_note_ids" set on each edition (in
editions.yaml or a sidecar), checked at build time and surfaced in
every UI.

### Phasing

These get added to the master plan (dev/PLAN_2026-05-07.md) under:
  - ν phase: master verse-popup switch (per-edition setting)
  - new ρ phase: per-item disable list + cross-tool sync infra

## Addendum #2 — Translation extractor tool

A new tool requested: ingest a public-domain Bible translation
(KJV, ASV, Darby, YLT, Bishops, Geneva, etc. — anything in USFM, OSIS,
or plain-text-with-verse-markers form), parse it, and align each
verse to the corresponding verse anchor in the master HTML.

Output: per-translation JSON (or YAML) mapping (book, chapter, verse)
→ translation text. Stored under `content/translations/<id>.yaml`
similar to how `content/scenarios/` stores hypothetical edition profiles.

Why this matters:
  - Powers the verse-translation popup feature (scope addendum #1)
  - Powers a future side-by-side translation comparison view (ξ.2)
  - Same architectural shape as the existing Strong's / TSK loaders
    in scripts/core/sources.py — those populate NOTES from external
    PD data; this populates TRANSLATIONS.

Phase placement:
  - New τ phase: ingestion / data acquisition tools
    τ.1  translation extractor (this item)
    τ.2  Strong's expansion (we have Hebrew; add Greek)
    τ.3  TSK expansion (already partial)
    τ.4  patristic citation database

## Addendum #3 — End-to-end "build my Bible" UI workflow

The complete end-user story:

  1. User opens the UI
  2. Picks a base edition (one of the 5 retail SKUs OR a saved scenario)
  3. Uses any/all of the tools we've built to modify settings:
       - /matrix         toggle symbols/kinds on/off
       - /sources        toggle individual notes/xrefs/sources/popups
       - (future ν)      customize symbols, themes, verse markers
       - (future ξ.2)    swap base translation
       - (future ν.4)    customize cover
  4. Clicks "Export My Bible"
  5. Gets a finished file (EPUB by default, possibly PDF, possibly print-ready)

Right now: the build pipeline is CLI-only (`ebible build`).
This addendum: wrap the existing build pipeline in a web UI export flow.

Implementation shape:
  - New /export route + UI panel
  - Pre-flight: show the user a summary of what they'll be exporting
    (book count, note count, kind set, customization choices) so they
    can sanity-check before committing to a long build
  - "Export" button → kicks off build_edition.py + build_epub.py
    (streamed progress to UI; build takes seconds-to-minutes)
  - Result: download link for the finished .epub
  - Optional: PDF export, print-ready PDF, web-viewer bundle

Critical: this is the BUY/DELIVER moment. It's the difference between
a development tool and a sellable product. Whatever the buyer's
journey looks like — landing page, payment, download — this UI
workflow IS the deliverable.

Phase placement:
  - New σ phase: end-user-facing build & export
    σ.1  /export route + pre-flight summary
    σ.2  one-click EPUB export (wraps existing pipeline)
    σ.3  PDF export
    σ.4  print-ready PDF (cover + interior)
    σ.5  web-viewer bundle (for embed in school websites)

This connects everything else. The whole tool stack becomes a buyer's
funnel: land → pick base → customize → preview → export → ship.

# ADDENDUM #4 (2026-05-07) — Publisher console + Bible-builder wizard
# ──────────────────────────────────────────────────────────────────

User context: "I want to be able to be in front of a buyer and show them
how easy it is to click a few buttons and there you go, the Bible you
wanted." Plus: "another UI tool for developer to be able to write in all
publisher things and copyrights, authors names and everything that needs
in the ID and also so they can add their own ISBN, again, any tool you
think a developer/publisher/or me can want to just put any of the
versions together the way I want."

This addendum splits into TWO new phases:

# π — Publisher Console (developer/publisher metadata)

Currently editions.yaml has minimal metadata: id, canon, title,
short_title, isbn, target_audience, notes, theme, verse_popups, etc.
What's missing is the full set of publishing identifiers a real
publisher needs to ship a book commercially:

  · Publisher (imprint) name + address + url
  · Author / contributor list with role tags (author, editor,
    translator, foreword, illustrator, etc.) — ONIX uses these
  · Copyright notice + year + holder
  · Trademark / acknowledgments
  · Publication date
  · Language code (ISO 639-1 / 639-2)
  · BISAC subject codes + Thema codes
  · Series name + series number (if part of a series)
  · Print ISBN, ePub ISBN, Mobi ISBN (separate identifiers)
  · DOI (if academic)
  · LCCN (if Library of Congress catalogued)
  · Cover credit (designer name + license)
  · Source-text credits (e.g. "based on the World English Bible,
    public domain")
  · Front-matter pages: title page, copyright page, dedication,
    foreword, preface, introduction, table of contents
  · Back-matter pages: acknowledgments, bibliography, indexes,
    about the publisher, also available

Implementation shape:
  · New /publisher route — full metadata editor UI
  · Per-edition settings stored as a `publishing` block in
    editions.yaml (preserves backward-compat: missing block = use
    defaults from build_onix.py)
  · build_onix.py rewritten to read these fields instead of the
    hardcoded values it has now
  · build_edition.py updated to inject this metadata into:
      - content.opf <metadata> block (EPUB-required)
      - the auto-generated copyright page
      - the title page
      - back-matter "about" page
  · Plain-text editors for front/back matter pages stored in
    content/front_matter/<edition_id>/*.html (or .md)

Phase placement:
  π.1  Publisher console UI + extended editions.yaml schema
  π.2  build_onix + build_edition wired to read publishing block
  π.3  Front-matter / back-matter editor (rich-text or markdown)
  π.4  Cover image upload + crop tool

# π.5 — Bible Builder Wizard (the buyer demo flow)

The thing the user demos in front of a customer. A stepped wizard
that walks through every choice in sequence:

  Step 1: Pick a starting profile     (clone an existing edition
                                        like catholic-study, or start
                                        from scratch)
  Step 2: Pick canon                   (87-book / 73 / 66 / custom)
  Step 3: Pick which note kinds to    (visual picker, see counts
          include                       per kind)
  Step 4: Pick a theme                 (see preview)
  Step 5: Set publisher info           (title, ISBN, author,
                                        copyright)
  Step 6: Optional: per-note refinements (jump to /sources)
  Step 7: Preview pre-flight summary
  Step 8: BUILD → download

Each step has a back button and remembers state. The final EPUB
filename incorporates the buyer-chosen edition title.

This phase is mostly composition — it stitches together the existing
/customize, /matrix, /sources, /export flows into a single guided
journey. Minimal new backend; mostly new frontend that reuses
existing endpoints.

Phase placement:
  π.5  Wizard UI (single page, multi-step)

# Why this matters

This addendum is the difference between "a tool to build Bibles" and
"a product a publisher will pay for". A serious publisher won't ship
a book with a stub copyright page. The Bible-builder wizard is the
demo Claude/the user needs in front of a buyer — it's the live
"watch this" moment.
