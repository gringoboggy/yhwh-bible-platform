## 1. CRITICAL findings (1 NEW + status of 12-C C1-C6)

### N-C1. γ.4 SOURCE corpus → `content/notes/` PROMOTE gap

**The flagship payload (γ.4 cluster, 830 entries spanning
Cyril-on-John, Cyril-on-Luke, Ephrem-on-Pentateuch, 1 Enoch,
Jubilees) currently does NOT have a verified path from
`content/sources/ethiopian_commentaries.json` into built EPUBs.**

**Evidence:**

- **Source corpus:** 830 entries across 9 books (verified via
  `EthiopianCommentaries()` direct query in this audit).
- **Promoted notes:** only **10** `comm-ethiopian` notes exist
  in active `content/notes/*.py` files, across 6 books (1en 1,
  1ki 1, exo 4, gen 2, lev 1, rut 1).
- **content/notes corpus total:** 51,394 notes — **unchanged
  since 2026-05-09**, despite the +825 source entries shipped
  in the γ.4 cluster during that window.
- **Build pipeline:** `scripts/build_edition.py` has ZERO
  references to `ethiopian_commentaries`, `EthiopianCommentaries`,
  `EthiopianCommentaryDetector`, or `comm-ethiopian`. The build
  reads `content/notes/*.py` only.
- **No integration test bridges the gap.** 12-C's WARN W11
  ("Build-pipeline integration test for Jubilees flowing into
  ethiopian-tewahedo EPUB") remains UNCONSUMED. This is exactly
  the kind of test that would have surfaced the gap weeks ago.

**Why the linter is blind:** `lint_rules.py` validates structural
file invariants (cross-link, encoder-order, freshness pairs). It
does NOT verify that source corpora reach build outputs. The
existing `attribute.py` audit counts only `content/notes/`,
which is why every audit-trail reports a clean 51,394.

**Implication for the buyer demo:** Per CLAUDE_PROJECT_RULES.md
§1 north star, the wizard's BUILD step produces "an EPUB with
that publisher's imprint, ISBN, copyright, theme, only their
picked notes, and verse popups in the languages they configured."
Today, that EPUB for the `ethiopian-tewahedo` edition surfaces
none of γ.4.1-D (Cyril-on-John, 116 entries), γ.4.2.C/D
(Ephrem-on-Exo/Num/Deu, 80 entries), γ.4.3-D (Cyril-on-Luke,
160 entries) — **356 of the project's most distinctive
patristic-payload entries.** Only the seed γ.4 work (~12 entries
promoted at γ.4 ship time) plus Genesis γ.4.2.B Ephrem (which
appears as 2 promoted gen.py notes) reaches the buyer.

**Two possible remediations — DECISION needed:**

- **Option A (promote-as-batch):** Run the detector → prospect
  → batch_promote_xrefs pipeline for `comm-ethiopian` across
  the 9 books in the source corpus. This is the χ-cluster
  pattern from §9 of CLAUDE_PROJECT_RULES.md. Approximate work:
  1 session including verification + voice-mix preservation
  + tests. Promotes ~800 entries into `content/notes/*.py`,
  growing the corpus from 51,394 → ~52,200 and surfacing the
  γ.4 work in built EPUBs.
- **Option B (live-detector at build):** Wire
  `EthiopianCommentaryDetector` (or its outputs) into
  `build_edition.py` directly, reading the source corpus at
  build time. This bypasses the `content/notes/` step. ~1-2
  sessions including cache invalidation + tests.

Option A is the documented project pattern. Option B is faster
to iterate (no promote step on each γ.4.x ship) but diverges
from the χ-cluster pattern. **Recommend Option A** unless the
user has a specific reason to keep the build pipeline static-
files-only.

**Severity:** CRITICAL for the buyer-demo north star. **Not
blocking the audit cadence — γ.4 content ships continue to be
internally consistent** (source-corpus growth + arc-close pins
all clean) — but the buyer doesn't see them yet.
