## 0. TL;DR

**Five things to fix before declaring v1.0:**

1. **SEC-001 (HIGH)** — `_send_file` serves `.svg` as
   `image/svg+xml` from `content/covers/`; an SVG with inline JS
   would XSS the localhost origin. Restrict the route to
   PNG/JPEG/WebP magic-bytes.
2. **SEC-002 (HIGH)** — `_read_body()` allocates `Content-Length`
   bytes before any per-route cap. A 2 GB Content-Length DoSes the
   single-threaded server. Cap at the read site.
3. **SEC-006 (MED)** — `subprocess.run` in `api_export_build` and
   peers has no `timeout=`. A stuck `build_edition.py` hangs the
   only thread. Add a per-call timeout + 504 on `TimeoutExpired`.
4. **EPUB-end-to-end smoke test missing** — `TestApiBuildAll`
   mocks `build_one`. No test opens a real built EPUB and asserts
   it has a TOC + OPF + expected note counts. A one-line
   regression in `_zip_epub` or theme injection ships broken.
5. **`scripts/web.py` is 7,169 lines / 50+ `api_*` handlers** —
   the single largest correctness/onboarding tax. The
   "one BaseHTTPRequestHandler" rule (§7.1) was meant to forbid
   Flask, not to forbid splitting handlers across files. Move
   route bodies to `scripts/api/<topic>.py`; keep `Handler.do_GET`
   doing only routing.

**Five things that would make this product genuinely unique** (§5):

A. **Time-traveling commentary** — filter notes by PD source date
   ("show me only commentary from before 1900"). Provenance is
   already in attribution; the reader UI is the missing piece.
B. **EPUB-as-the-app** — the shipped EPUB embeds enough JS to
   re-customize itself. Genuinely never been done.
C. **Grounded RAG Q&A** — Anthropic infrastructure already
   wired (χ-AI-xrefs / χ-AI-notes); pivot to *read-time*
   answers grounded only in the user's edition. Differentiated
   from generic LLM Bible chat because the grounding is bounded.
D. **Manuscript-scan integration** — show the actual Codex
   Sinaiticus / Vaticanus page for a verse. PD scans exist.
   Massive demo wow factor.
E. **Lectionary-aware reader** — the reader opens to today's
   liturgical reading. χ.11 ships the data; the reader mode is
   the consumer hook.

The first four bundle gives coverage map + 4× faster test runs +

## 1. Security — adversarial findings

Threat-model lens: single-user desktop, but `--host 0.0.0.0` LAN
share is documented. Findings ordered by severity. **None of these
are duplicates of ξ.1/ξ.2/ξ.4/ξ.6/ξ.10/ξ.11/ξ.13/ξ.15** which the
team has already shipped.

### HIGH

- **SEC-001 — SVG covers as XSS sink.** `scripts/web.py:6133-6141`
  (`_send_file` MIME map) used by `/content/covers/...` route at
  `web.py:6585-6604`. Cover-serve route trusts file extension; an
  `.svg` placed in `content/covers/` (via backup/restore, manual
  drop, or scenario import) renders inline `<script>` when
  navigated directly. The upload validator rejects SVG today; the
  *serving* route does not. **Fix:** drop SVG from MIME map; only
  serve png/jpeg/webp magic-bytes-verified; add CSP
  `default-src 'none'; sandbox` to image responses.

- **SEC-002 — Multipart parser unbounded body read.**
  `scripts/web.py:3087-3139`. `_read_body()` allocates
  `Content-Length` bytes BEFORE any per-route cap fires. A peer
  sends `Content-Length: 2_000_000_000` and the server tries to
  alloc 2 GB. **Fix:** in `_read_body`, reject
  `Content-Length > 32 MB` (or per-route ceiling) before
  `self.rfile.read()`. Cap header_blob in `_parse_multipart` at
  8 KB per part (RFC ceiling for boundary is 70 chars but headers
  get bigger).

- **SEC-003 — RSS Host header reflection.**
  `scripts/web.py:6362-6367` builds RSS link URLs from
  `X-Forwarded-Proto + Host` with no allowlist. LAN peer or
  malicious page can pin attacker URLs into the feed. **Fix:**
  honor Host only if it matches `localhost` / `127.0.0.1` /
  configured allowlist; otherwise use a hardcoded base URL.

### MEDIUM

- **SEC-004 — `cache_path` from `_fetchers.json` not
  path-confined.** `web.py:1889`. A scenario bundle that swaps
  `_fetchers.json` could direct writes outside the cache dir.
  **Fix:** validate via `safe_path.resolve_under` (which
  exists and is correct).

- **SEC-005 — Audit log has no integrity chain.**
  `scripts/core/audit_log.py:70-107`. The "append-only" property
  is policy not enforced; any process can rewrite history.
  Marketed as compliance trail. **Fix:** add `prev_hash` per line
  (sha256 chain); verify on `read_recent`. Also add a redaction
  allowlist for `api_key`/`password`/`token`/`secret` before log.

- **SEC-006 — `subprocess.run` has no timeout.**
  `scripts/web.py:2054` (`api_export_build`), and others. A stuck
  build hangs the only thread and DoSes the UI. **Fix:**
  `timeout=300`; return 504 on `TimeoutExpired`. (`epubcheck.py`
  is the reference — already does this.)

- **SEC-007 — Empty `boundary=` accepted silently.**
  `web.py:3142-3154`. Defense-in-depth gap. **Fix:** reject empty
  or > 70 char boundaries; 400 from caller.

### LOW

- **SEC-008 — `_resolve_content_path` doesn't reject Windows
  drive letters.** `web.py:4742-4769`. Fails closed today via
  `relative_to`, but the explicit-reject layer is missing — drift
  risk. Mirror `safe_path._check_string_safety`.

- **SEC-009 — `"python3"` literals across dev scripts.**
  `build_edition.py:2549`, `release.py:64,80,266`, `bulk_edit.py:190`,
  `add_note.py:252,260`, `add_kind.py:178`, `verify.py:38`,
  `ship-check.py:38`, `run.py:118`. PATH hijack vector on dev
  machines. Use `sys.executable` (web.py:2046 already does).
  Add a `lint_rules.py` check.

- **SEC-010 — `Cache-Control: public` on localhost-app responses.**
  `web.py:6148`. Should be `private`.

- **SEC-011 — YAML billion-laughs DoS.** `web.py:1170-1179`,
  `api_import_scenario_yaml`. PyYAML `safe_load` on 64 KB of
  anchored YAML can blow up. Wrap in a thread-watchdog or
  pre-scan for `&`/`*` density.

### Threat-model observations (NOT findings)

- No `pickle` / `yaml.load` / `exec` anywhere — `ast.literal_eval`
  remains the only data-load primitive. Solid.
- No real secrets in repo (`.env.example` has only the
  `sk-ant-...` placeholder).
- `_check_admin_auth` uses `hmac.compare_digest` correctly.
- `safe_path.resolve_under` is correct.
- The Anthropic surface (`scripts/core/sources.py:1268-1315`)
  uses structured-output JSON schema with `additionalProperties:
  false` and the model output flows through `sandbox_ai_html`
  (ξ.15) before promotion. Solid.

**Recommended phase:** **ξ.16** — single-session security
sweep covering SEC-001/002/003/006. SEC-004/005 each warrant
their own ξ.x phase. Total: ~2 sessions to close every HIGH +
MED finding.

## 2. Architecture — biggest leverage points

### The god-module: `scripts/web.py` (7,169 lines)

- 50+ `api_*` business helpers (lines 298-5935)
- A 1,100-line `Handler` class (6016-7144)
- A 450-line hand-maintained `do_GET` route cascade
  (6206-6650+) with comments admitting the ordering is brittle
  ("more-specific routes must precede the bare-list")
- Mixes signature/cache plumbing, tuple↔dict conversion, YAML
  patchers, multipart parsing, the snapshot/diff engine

**The fix is not Flask.** A `ROUTES = [(method, regex, handler), ...]`
table compiled once at import is safer, lintable, and self-
documenting without touching the no-framework rule. Per-topic
modules at `scripts/api/<topic>.py` keep the
`BaseHTTPRequestHandler` constraint while letting each route body
move out of the god-module. Cross-link invariant test (§6.2)
already enforces what consoles exist; an analogous test would
enforce route table completeness.

### Other smells worth fixing

- **Duplicate `load_notes` in `scripts/note_quality.py:151-168`**
  bypasses the `notes_io` cache. Phase β.2 supposedly consolidated
  five duplicates; this one survived. Plus
  `_load_note_quality_helpers` (`web.py:160-167`) re-imports it
  via `importlib.spec_from_file_location` — creating a parallel
  module identity that defeats the cache further. **Fix:** plain
  `import scripts.note_quality as _nq`.

- **`api_matrix` re-walks `config.load_books()` 3× per request**
  (`web.py:454-529`). 87 books × 3 calls × 5 editions = wasted
  scans. **Fix:** lift to local once.

- **`Matrix.per_chapter` has 4-level nested dict with mixed
  int/str keys** (`core/matrix.py:99`). The "JS handles either"
  comment is a smell. **Fix:** flat `dict[tuple, int]` or typed
  `@dataclass`.

- **Observability gap.** When `build_edition.py` fails at 3am,
  the user gets "see server log." No run-id, no phase indicator,
  no path to half-written output. **Fix:** structured per-build
  jsonl log + run-id echoed in 500 response.

- **`_files_signature` lru_cache scar** at `web.py:96-101` is
  CHANGELOG content in source. Delete the historical paragraph.

- **`AI_DRAFTED_KINDS = frozenset({"comm-ai"})`** (one element)
  is the project's anti-pattern of premature abstraction. Keep
  for now (the documentation value is real and the cost is
  zero), but if it stays a singleton through 3 more phases,
  inline it.

### Bold proposal — derived SQLite index

Today, every aggregate question (matrix, citation index,
glossary, attribution audit, search, coverage, dashboard)
re-walks 87 books × N notes through 7+ separate `lru_cache`
wrappers, each with its own signature scheme. Architectural cost
grows with every new aggregate.

**Treat `content/notes/*.py` as an append-only event log with a
derived SQLite index rebuilt on note write.** The .py files stay
canonical (byte-equivalent diffs preserved); `ast.literal_eval`
stays the trust boundary; the index is purely derived. Every
aggregate becomes a sub-millisecond query. The `lru_cache` zoo
collapses to one rebuild trigger (mtime-keyed).

**Why it's safe:** SQLite is stdlib (`sqlite3`); no new
dependency; can be rebuilt from scratch on every startup if
trust is needed; every existing test stays green because the
.py files don't change.

**Why it's high-leverage:** matrix lazy-loads become trivial,
search becomes a real feature instead of a future phase
(`υ.3`), arbitrary new aggregates ship in hours not sessions.

This is a 2-3 session phase, but it would unlock every UX
improvement on the roadmap.

## 3. Tests — coverage + perf gaps

### Highest-risk untested paths

1. **`scripts/build_edition.py:2226 build_one()` — no real EPUB
   end-to-end.** Closest test (`test_build_one_stats_*`) uses
   `dry_run=True`. `TestApiBuildAll` mocks `build_one`. No test
   opens `zipfile.ZipFile(epub).namelist()` to assert TOC + OPF
   + note counts. **A regression in `_zip_epub` or theme
   injection ships broken.** Add a single
   `test_e2e_build_each_edition` that loops the 9 editions, calls
   non-dry-run `build_one`, opens the EPUB, asserts structural
   invariants.

2. **`scripts/core/snapshots.py:103 _corpus_fingerprint()` hashes
   `(stem, mtime_ns)`, not content.** Tests only check
   "40-hex-chars". `git checkout` resetting all mtimes equates
   two different corpora. **Fix:** sha256 content hash.

3. **`scripts/core/sources.py StrongsHebrew` (line 77)** — no
   dedicated `TestStrongsHebrewSourceLoader` (Greek and Naves
   have full coverage; Hebrew is the gap).

4. **`scripts/core/detectors.py:444 CrossRefDetector` (TSK)** —
   no `TestCrossRefDetector` class. The foundational xref
   engine, used by every χ-cluster downstream. `min_votes=30`
   threshold unpinned.

5. **No corpus-wide invariant test.**
   `test_book_returns_notes_in_canonical_order` (test_scripts.py:
   1434) only checks `gen` via API. Nothing iterates all 87 book
   files asserting `notes == sorted(notes, key=(ch, vs, suffix))`.
   A bulk edit reordering one obscure book wouldn't fail
   anything. Add one parametrized test.

### Structural

- **Stale corpus floor `>= 1381`** in test_scripts.py:1432, 1452,
  5109. Set 2026-05-08; corpus is now ~50K. Per-book floors
  (e.g. `gen ≥ 200`, `psa ≥ 150`) checked into a `BOOK_FLOORS`
  dict in `dev/CLAUDE_PROJECT_RULES.md` §8 would catch
  per-book regressions.

- **No per-edition kind-set pin.** A typo
  (`comm-rabbic` vs `comm-rabbinic`) silently drops a kind,
  caught only by the loose corpus-floor check. Pin each of the
  9 editions' enabled-kind set explicitly.

### Perf

- **33 tests spin up live HTTP servers.** Estimated 5-15s
  saveable by switching to `wsgiref` direct-call or shared
  module-scope fixture.

- **`pytest -n auto` is viable.** Most tests are isolated.
  `editions.yaml` mutators (`test_save_round_trip_preserves_*`,
  line 1249) need `@pytest.mark.serial` or filelock. With 6
  workers, expect 219s → ~50-60s.

- **`test_perf.py` has `_PYTEST_HARNESS_MULTIPLIER=1.4`** (line
  97) hiding cold-cache regressions. Flag for review.

### Skip markers — checked

- `test_audit_dead_code.py:26`, `test_audit_types.py:21`,
  `test_lint_rules.py:729` — legit (dev-tool absence).
- `test_perf.py:51 — pytest.skip("gen.py not present")` is
  stale defensive code; gen.py is always present. Delete.
- `test_scripts.py:8094, :8097` — Greek-keyword sparse-data
  branches likely never fire after ψ.8. Re-check; if dead, the
  branch they guard is also dead.

**Recommended phase:** **ω.34** — tests pass: add EPUB e2e,
content-hash fingerprint, per-edition kind pins, per-book
corpus floors, install pytest-xdist + serial markers. ~1.5
sessions; lifts test wall-time from 219s to ~60s and closes
five real coverage gaps.

## 4. Matrix — specific UX/scaling wins

### Data-model wins

- **Compute fewer projections.** `compute_matrix()` returns 5
  parallel grids (`enabled`, `potential`, `per_book`,
  `per_chapter`, etc.). `enabled` is `potential` filtered;
  `per_book` is `per_chapter` summed. Storing redundant
  projections triples cache footprint and means partial
  invalidation has 3 forget-points. **Keep one canonical
  `Counter[(ed, kind, book, chapter)]`; project on demand.**

- **Don't ship the full per-chapter cube on every page load.**
  5 ed × 63 kinds × 87 books × ~30 chapters = ~820K entries
  even mostly empty. Fine at 51K notes; multi-MB at 200K.
  **Lazy-load per-chapter via
  `/api/matrix/chapter?ed=X&kind=Y&book=Z` on drilldown
  expansion.** The `TOP_N_BOOKS = 5` cap (matrix.py:1675)
  proves the UX already knows most of the cube isn't shown.

### UX wins that scale with edition count

- **The sticky-column CSS is a band-aid.** With 12 editions the
  matrix won't fit. **High-leverage move:** transpose at >7
  editions (kinds as columns), OR pivot to a "per-edition card"
  view (one card per edition, mini kind-grid inside).

- **Scenario concept is half-step.** Saved kind-set that loads
  into an edition. But scenarios don't compose ("Catholic kinds
  + my custom xrefs" impossible), can't diff against the
  edition they came from, and live separate from
  `editions.yaml`. **Either make first-class** (compose / diff /
  inherit) **or kill them** — let publishers save edition drafts
  directly.

- **Split the 2,209-line `templates/matrix.py` template-string.**
  ψ.18 + ψ.18.1 + ψ.18.2 + ψ.20 + ψ.26 + ψ.27 + ψ.28 + ψ.29 = 8
  phases of accreted JS in one HTML blob. No JS lint, no module
  boundaries. Even without a build step, splitting into
  `templates/matrix_html.py` + `templates/matrix_app.js` (served
  as `/static/matrix.js`) gives syntax highlighting,
  browser-cacheability, and smaller diffs.

**Recommended phase:** **ψ.34 (matrix data-model
consolidation)** — collapse 5 projections to 1, lazy-load
per-chapter, split JS out. ~1 session; unblocks 9-edition and
beyond scale.

## 5. "Make it unique" — product-direction proposals

The agents covered code/security/tests/tools. None covered
product. These five would make this Bible publishing platform
genuinely distinctive in a category dominated by static apps.

### A. Time-traveling commentary

The corpus already has provenance per note (PD source +
attribution + estimated date). The reader UI doesn't surface
it. Add a "show me only commentary from before YYYY" filter.

- **Why unique:** zero competitors do this. Wycliffe, YouVersion,
  Logos, Olive Tree all surface modern commentary as undated.
- **Why for THIS project:** χ.0 (Kenyon), χ.1 (Strong's Greek),
  χ.6 (TSK), χ.7 (Nave's Topical) all have known publication
  dates. The infrastructure is 90% there.
- **Effort:** ~1 session. Add `source_year` to attribution;
  expose a year-range slider in the reader; filter the popup
  set by date.
- **Demo value:** "Let me see how Christianity understood John
  3:16 in 1500 vs 1700 vs 1900" is a wow moment.

### B. EPUB-as-the-app

The shipped EPUB embeds enough JS that the reader can
re-customize themselves and re-export. The artifact IS the
publishing house.

- **Why unique:** literally never been done. EPUB 3 supports JS;
  no one has used it for this.
- **Why for THIS project:** the customize console is already
  HTML/JS with no build step. The EPUB JS subset is a strict
  subset of the customize console's. The data is already in the
  EPUB (notes, kinds, canon). All that's missing is a "self-
  customize" panel inside the reader.
- **Effort:** 2-3 sessions. Most work is figuring out
  EPUB-reader JS compatibility (Apple Books / Kobo / Calibre).
- **Demo value:** "This Bible can edit itself." Astonishing.
- **Risk:** some EPUB readers strip JS. Mitigation: degrade to
  read-only when JS is unavailable. Same product as today, plus
  the magic on supporting readers.

### C. Grounded RAG Q&A — bounded to the user's edition

χ-AI-xrefs and χ-AI-notes already wire Anthropic at *build
time*. Pivot to *read time*: a "Ask this Bible anything"
console that grounds answers exclusively in the user's
edition's notes + verses. No external knowledge.

- **Why unique:** every "AI Bible" today routes to ChatGPT
  general training. A bounded RAG over a curated PD corpus is
  philosophically different — answers cite only what the
  publisher chose to include. Editorial integrity at the AI
  layer.
- **Why for THIS project:** corpus is in one schema; embeddings
  via Voyage AI are already on the deferred list; the auth +
  audit log already exist for cost-gated paid runs.
- **Effort:** 3-4 sessions. Embedding pass + retrieval + a
  `/ask` console.
- **Demo value:** the buyer asks "how does this edition handle
  the Trinity?" — the system cites 4 PD commentaries from this
  edition, none from outside. Defensible, traceable answers.
- **Risk:** hallucination. Mitigation: refuse to answer when
  retrieval returns < N chunks above similarity threshold;
  always cite chunks; never assert without grounding.

### D. Manuscript-scan integration

For each verse, optionally show the actual manuscript page
from a public-domain codex (Sinaiticus, Vaticanus,
Alexandrinus all have full PD scans).

- **Why unique:** academic Bibles do this in print; consumer
  apps don't.
- **Why for THIS project:** the χ.0 Kenyon ingest pipeline is
  the same shape — fetch PD source, store, reference. Codex
  page references are already in some Kenyon notes.
- **Effort:** ~2 sessions. Fetch + store the page-level scan
  index; render alongside the verse.
- **Demo value:** "see the actual ink" sells. Buyers physically
  lean toward the screen.

### E. Lectionary-aware reader mode

The reader knows today's date and surfaces the lectionary
readings for that day in the appropriate tradition (Catholic,
Anglican, Eastern Orthodox, ELCA, RCL).

- **Why unique:** lectionary apps exist (Universalis, etc.)
  but they're separate. Bible apps don't usually bake in the
  liturgical calendar.
- **Why for THIS project:** χ.11 spec already lays out the
  feast/calendar data layer. The consumer-facing wiring (open
  reader → "Today's Reading") is the missing piece.
- **Effort:** χ.11 + ~0.5 session for the reader-mode UI.
- **Demo value:** for the Catholic / Orthodox / Anglican
  buyer, this is the difference between "a Bible" and "MY
  Bible." Critical for tradition-aligned editions.

### Honorable mentions

- **Memory-verse spaced repetition** (Anki-style scheduler in
  the reader; bonus: publishable as a "Memory Bible" sub-
  edition)
- **Polyglot side-by-side reader** (Greek + Hebrew + KJV + WEB
  parallel columns; niche but academia would pay)
- **Read-only public API** (canonical PD-Bible-API; no one owns
  this slot)
- **Hebrew/Greek pronunciation audio** (smaller scope than full
  audio Bible; easier ship; differentiator for language
  learners)
