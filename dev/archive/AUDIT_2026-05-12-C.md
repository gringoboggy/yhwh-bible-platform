### C2. Book codes `joh` and `ps` are NOT in `content/books.yaml`

**Files+lines:** `content/sources/ethiopian_commentaries.json`
(119 `joh` entries + 2 `ps` entries) vs. `content/books.yaml`
(registers `jhn` and `psa`).

**Evidence:** Entries use `book: "joh"` (Cyril's dense Johannine
commentary) and `book: "ps"` (2 Ephrem-on-Psalm-1 entries), but
`books.yaml` registers the canonical codes `jhn` ("The Good
News According to John") and `psa` ("The Psalms"). A call to
`for_verse('jhn', 1, 1)` returns `[]` even though Cyril ships
dense John 1:1 Logos-prologue coverage.

**Scope:** Pre-existing corpus-wide — `catholic_commentaries.json`,
`protestant_commentaries.json`, `reformation_commentaries.json`,
and `rabbinic_commentaries.json` all use `joh`/`ps` too. Not
introduced by γ.4.5; the audit surfaced it.

**Why the linter is blind:** `lint_rules.py` validates structural
file invariants and cross-references; it does not validate that
JSON-content book codes resolve against `books.yaml`.

**Action:** Two options:
- **Option A (preferred):** Add aliases in `scripts/core/sources.py`
  loader or in `books.yaml` itself — `joh→jhn`, `ps→psa` —
  exposed via `for_verse` so reader-side code can use either
  code transparently. Approximate work: 30 lines.
- **Option B:** Rewrite all 5 commentary JSONs to use the
  canonical codes. Approximate work: 1-line `sed`-equivalent
  per JSON × 5 files = 5 minutes, but invalidates all existing
  tests that reference `joh`/`ps` strings.

**Severity:** CRITICAL because it BLOCKS the John pericope from
surfacing in any built EPUB. 119 Cyril-on-John entries are
currently un-routable to the build pipeline. This is a demo
blocker.

### C5. Preflight cache-invalidation test FAILING

**Files+lines:** `tests/test_scripts.py::TestEditionMeta::test_preflight_caching_invalidates_on_notes_change`.

**Evidence:** Warm read 13.9s, cold-after-edit read 11.1s. The

**Implication for the demo:** preflight may serve stale `pass`
verdicts after content edits, masking new failures during a
live demo edit-and-rebuild flow. If the buyer customizes a
note in /customize and rebuilds, the preflight dashboard might
not detect that the rebuild needs to happen.

**Action:** Investigate `_files_signature` / `_notes_dir_signature`
interaction with the now-590-entry `ethiopian_commentaries.json`
— the timing implies warm read is already paying the full
load. Possible root cause: the 590-entry JSON is large enough
that even the cached path is slow, narrowing the warm/cold
gap below the 5× threshold.

**Severity:** CRITICAL because it's a real demo-flow risk, not
just a test flake. Should be triaged before the next significant
content ship.
