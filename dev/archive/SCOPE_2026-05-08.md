## 1. The end goal — unchanged from origin

```
A schoolteacher, parish priest, or independent publisher can land
on the platform, customize any of 5+ editions (Ethiopian, Catholic,
Protestant, Orthodox, Tanakh) without YAML, CLI, or build-pipeline
knowledge, click BUILD, and walk away with a real EPUB carrying
their imprint, ISBN, theme, only their picked notes, and verse
popups in the languages they configured.
```

The buyer demo is unchanged. **What's added in this scope refresh:**
the platform itself becomes a desktop application a non-technical
person can install and use, and the corpus reaches its 35-40K target
through proven χ-cluster pipeline patterns plus a UI affordance that
makes user-side source ingestion painless.

## 2. Universal principles (carried forward verbatim)

These are non-negotiable and unchanged from the 05-07 scope:

1. **Fully customizable.** Every UI element, symbol, marker, kind
   name, category, color, label — assume the user will want to
   change it. Defaults exist; nothing is hard-coded.
2. **Easy.** No YAML hand-editing required. No CLI knowledge
   required. No build-pipeline knowledge required.
3. **Verifiable by book/chapter order.** Every browsing /
   management UI defaults to canonical reading order
   (Genesis → Exodus → … → Revelation, ascending chapters).
   Hard requirement, not stylistic preference.
4. **Schema additions are additive.** New YAML fields default to
   back-compat; builds are byte-identical when new fields are
   unset. (Source: §9 mental models.)
5. **Web consoles WRAP CLI tools, never replicate them.**
   The 47-script CLI surface is the source of truth.

## 4. Two new strategic vectors

This scope refresh adds two clusters that weren't in the 05-07 doc:

### 4a. Cluster σ — version control + collaboration (NEW)

The user has been receiving zip files for every save. This is a
real friction at this point — the project is 50 MB unpacked, and
the dev/SESSION_STATE + dev/IN_FLIGHT + dev/CHANGELOG protocol is
expensive to keep in sync via zip-and-unzip. **GitHub backup via
Claude Code is the answer.** Not pushing anywhere public — just
private-repo storage + git as the handoff mechanism.

```
σ.3  GitHub backup via Claude Code        NEW
      Claude Code installs as one-time setup; git becomes the
      session handoff (clone at start, push at end). User does
      no public-vs-private toggling — Claude can create a private
      repo on the user's behalf and push, but cannot make it
      public or add collaborators (access-control changes are
      explicitly prohibited in the safety policy).
      Effort: 1 session (mostly walking the user through Claude
      Code install).
      Risk: LOW — read/write to user's own private storage only.
```

(σ.1 / σ.2 — the original σ-letter assignments to "buyer-facing
export pipeline" — were shipped as v28a-42. The σ letter is
re-used here for the version-control story since it's
conceptually the same family: "ship the work somewhere stable.")

### 4b. Cluster θ — desktop binary (NEW)

The platform is far enough along that wrapping it as a real binary
is a 3-4 phase project, not a year. Cluster θ is the desktop story.

```
θ.1  One-click launcher (PyInstaller wrapper)        NEW
      A native binary the user double-clicks. Internally: starts
      the existing scripts/web.py server in a thread, opens the
      user's default browser to localhost:8000. Zero terminal,
      zero pip-install for end users.
      What changes for the user: zero command-line knowledge needed.
      What stays the same: the UI is still browser-rendered;
      consoles unchanged.
      Output: one binary per platform (.app / .exe / .AppImage).
      Effort: 1 session.
      Risk: LOW — wraps existing working server.

θ.2  Native shell (PyWebView around existing consoles) NEW
      Same backend; UI rendered inside a native window — no
      address bar, native menu bar, native file dialogs (cover
      uploads through the OS picker, "Save EPUB to…" through the
      OS save dialog).
      What changes: feels like a real app — File menu has
      "Open project folder", "Export EPUB", "Settings".
      What stays the same: all 13 consoles unchanged.
      Effort: 1-2 sessions.
      Risk: MED — IPC bridge for file dialogs is the new code.

θ.3  Auto-update (Sparkle / winsparkle pattern)        NEW
      Once a binary is shipping, auto-update is table-stakes.
      Standard pattern: signed manifests + delta downloads.
      Effort: 1-2 sessions.
      Risk: MED.

θ.4  Cross-platform installers (DMG / MSI / AppImage)  NEW
      Wraps θ.1 output in proper installers. PyInstaller alone
      gets you a binary; this gets you a *user-friendly install
      experience*.
      Effort: 1 session.
      Risk: LOW.
```

### Per-user data location refactor (mandatory before θ.1)

Today the project assumes the working directory IS the project —
`content/notes/` lives next to `scripts/`. For a desktop install
this has to flip: binary lives in `/Applications`, user data lives
in `~/Library/Application Support/EthiopianBible/`.

```
ω.5  Per-user data location refactor                  PROMOTED
      Every Path(__file__).resolve().parent.parent / "content"
      becomes user_data_dir() / "content". A back-compat shim
      checks for in-tree content/ first (development mode), falls
      back to user-data-dir (installed mode). One focused phase.
      Effort: 1-2 sessions.
      Risk: MED — touches every script that reads/writes content.

      (ω.5 was previously assigned to "Multi-user/reviewer roles"
      which is now indefinitely deferred; the letter is reused for
      the per-user paths story since it's still in the operational
      family.)
```

## 7. v1.0 — what counts as a release

The 05-07 scope had no defined terminus. The new shape gives one:

```
v1.0 = θ.2 shipped (native shell) + χ.1 shipped (Greek lexicon) +
       corpus ≥ 25,000 notes (~70% of target).

A real person can install the desktop app, customize any of 5+
editions, build a real EPUB with their imprint, and the apparatus
they see is dense enough to feel like a published study Bible.
```

**Everything past v1.0 is point-update territory:** θ.3 auto-update,
θ.4 installers, ψ.1 live preview, χ.2-5 commentary detectors, υ.2-6
console-surfacing of CLI tools, ψ.7 edition templates. Each can ship
as an independent v1.x release.

## 8. What this scope does NOT mean

- "Everything in one session" — no. This is months of work taken in
  the right order. The PLAN doc has the sequencing.
- "Rebuild what already works" — no. The 13 consoles + 47 CLI scripts
  + 393 tests are the foundation. Every new phase wraps or extends
  rather than replaces.
- "Make a public app" — explicitly no. σ.3 keeps the GitHub repo
  private; θ ships a binary the user runs locally; cloud / multi-user
  hosting is a future scope, not this one.
- "Drop the corpus push for desktop work" — no. χ.1 still happens,
  just sequenced after the desktop foundation lands so the live
  preview wow moment has dense apparatus to show.
