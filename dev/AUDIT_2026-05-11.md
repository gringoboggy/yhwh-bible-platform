### 1.2 New architectural findings (this audit)

#### ARCH-01 (HIGH leverage) — `scripts/web.py` is now 7,395 lines

The 2026-05-10 audit recommended a `ROUTES = [(method, regex,
handler_fn), ...]` table compiled once at import + per-topic
`scripts/api/<topic>.py` modules. **None of this happened.**
Worse: the file grew by 226 lines this arc as 12 phases all
landed handlers / patches into it.

Concrete pain points:

- `do_GET` / `do_POST` / `do_PUT` are still long if/elif cascades
  with comments admitting "more-specific routes must precede the
  bare-list" — a precedence ordering that has zero compile-time
  enforcement.
- 50+ `api_*` business helpers live alongside multipart parsing,
  path-resolution helpers, snapshot/diff engine, and the
  Handler class. Single file = single mental-model bottleneck.
- The §6.2 cross-link linter enforces console-cross-links but
  there is no analogue enforcing route-table completeness or
  `api_* ↔ tests/test_scripts.py::TestApi*` pairing.

Proposed phase: **`ω.35-A web.py route table`** (1 session) ships
the table + route-completeness linter without splitting files yet.
**`ω.35-B web.py topic split`** (1-2 sessions) moves
`scripts/web.py` business helpers into `scripts/api/<topic>.py`
keeping `Handler.do_GET` doing only routing.

#### ARCH-02 (MED leverage) — fingerprint stat-walk is the Δ.4.1 blocker

Diagnosed from `scripts/core/matrix.py:221-232` docstring +
`scripts/core/corpus_index.py:rebuild()`:

> Even with the lock serializing writes, every `compute_matrix()`
> call triggers a fingerprint stat-walk + potential rebuild at
> the corpus_index layer, which interacts badly with the test
> suite's expectation of a memory-cached compute_matrix.

The root cause: `corpus_index.connection()` calls `rebuild()`
which calls `_compute_fingerprint()` which `os.stat`s every
`notes/*.py` file. 87 stat calls per query is fine in cold-cache
isolation but hammers the test suite's xdist workers.

Proposed phase: **`Δ.6 — fingerprint cache layer`**.
~50 lines. TTL-memo `_compute_fingerprint()` keyed on a
monotonic clock with a configurable refresh interval (default 1s
in production, 0s in tests). Memo invalidated by `invalidate()`
explicitly. After Δ.6, `connection()`'s rebuild check is a
single dict-lookup in steady state.

Once Δ.6 lands, **Δ.4.1, Δ.2.1, Δ.3.1, Δ.5.1 wire flips all
become safe one-liners** in production (test suite still might
need `monkeypatch.setattr(corpus_index, "_FINGERPRINT_TTL_SEC",
0)` for force-rebuild patterns).

#### ARCH-03 (MED leverage) — `compute_matrix()` 5 projections → 1

The audit's §4.1 recommendation. Currently:

```python
@dataclass(frozen=True)
class Matrix:
    enabled: dict[str, dict[str, int]]                       # ed → kind → count
    potential: dict[str, dict[str, int]]                     # ed → kind → count (canon-only)
    edition_canon_books: dict[str, set[str]]                 # ed → set[book]
    edition_enabled_kinds: dict[str, set[str]]               # ed → set[kind]
    per_book: dict[str, dict[str, dict[str, int]]]           # ed → kind → book → count
    per_chapter: dict[str, dict[str, dict[str, dict[int, int]]]]  # ed → kind → book → chapter → count
```

`enabled[ed][k]` ≡ `potential[ed][k] if k in edition_enabled_kinds[ed] else 0`.
`potential[ed][k]` ≡ `sum(per_book[ed][k].values())`.
`per_book[ed][k][b]` ≡ `sum(per_chapter[ed][k][b].values())`.

**Three of the five projections are derivable.** The cache
footprint is ~3× what's needed. Worse: every consumer of
`compute_matrix()` has to know which projection to read; there's
no single source of truth.

Proposed phase: **`ψ.35` — collapse to one canonical
`Counter[(ed, kind, book, chapter)]`** with cached projection
helpers (`m.per_book(ed, kind)` → dict). Multi-consumer
refactor (15+ web.py call sites); needs careful per-consumer
migration. Ship `ψ.35-A` data-model first behind a feature flag
or new method, migrate consumers one at a time as `ψ.35-B`...,
flip default in `ψ.35-Z`.

This pairs naturally with **Δ.4.1 wire flip** — both touch
`matrix.compute_matrix()`.

#### ARCH-04 (LOW leverage) — duplicate `load_notes` survives in note_quality.py

Audit-flagged 2026-05-10. Still there. 5-minute fix. Should be
a one-liner in any future cleanup phase.

### 2.2 Gaps to "full optimization for most-professional result"

**Performance ceiling:** with 9 editions × 63 kinds × 87 books ×
~30 chapters = ~1M cells in the per_chapter cube, even sparse
storage is ~25 MB serialized JSON. Today the API ships the whole
cube on every page load. **At >12 editions or >100K notes, this
breaks.** The audit projected this at "multi-MB at 200K notes."
Today's notes count (51K) puts us at ~half of the danger zone.
The fix is `ψ.36 lazy-load /api/matrix/chapter` — currently
parked needing UI co-design.

**Cache-footprint ceiling:** `lru_cache(maxsize=1)` holds the
full `Matrix` dataclass across all 6 projections. At 9 editions,
~25 MB resident. Going to 15 editions doubles it. The fix is
`ψ.35 data-model collapse` — currently parked.

**UX ceiling at scale:** sticky-column CSS works to ~7 editions.
Today's 9 editions already overflow on mobile/tablet. The
audit's recommendation: transpose to "kinds-as-columns" or pivot
to per-edition card view at >7 editions. Bundles with `ψ.32`.

**Onboarding ceiling:** 1,552-line `matrix_app.js` has no module
boundaries. The selection state machine, scenarios machinery,
undo/redo, sidebar widgets, and density heatmap all share a flat
`window`-scope namespace. Future Claude reading it sees one big
ball. The fix isn't a bundler (project rule §6.3 says no build
step) — it's logical ESM-style modules served as separate
`/static/matrix-*.js` files (loadable via `<script type="module"
src="...">`). Defer to a future phase if the app keeps growing;
not blocking today.
