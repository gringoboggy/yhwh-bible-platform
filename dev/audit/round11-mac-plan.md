## gap4 — Shared process-global _CACHED_CONN (sqlite3.connect(check_same_thread=False)) is READ — conn.execute() — outside _CONN_LOCK by every query helper, while invalidate()/rebuild()/_build_to() can close that same handle under the lock; the lock makes the close/swap atomic but does NOT span the reader's execute, so each reader/writer pair is a use-after-close race window under ThreadingHTTPServer + the build ThreadPoolExecutor(max_workers=5).

**Sites:** 18 confirmed (round-10 reported 16; 0 false-positive, 2 missed-then-found by the critic).

**Canonical fix (apply at EVERY site below):** Make _CONN_LOCK span the actual query, not just the open/close, so a reader and a closer can never overlap on the same handle. The canonical fix WIN should apply at EVERY reader site: replace the `conn = connection(); ... conn.execute(...)` pattern with a single context-managed helper that holds _CONN_LOCK for the whole read. Concretely, add to corpus_index.py:\n\n    @contextlib.contextmanager\n    def _read_cursor():\n        with _CONN_LOCK:\n            conn = _ensure_conn()   # the body of connection() AFTER rebuild(), i.e. the open/swap, run while already holding the lock; rebuild() itself stays OUTSIDE the lock as today\n            yield conn              # invalidate()/rebuild()/_build_to() also take _CONN_LOCK to close, so they now block until the reader's execute+fetchall completes\n\nand rewrite every helper (count_by_kind, count_by_book, count_by_kind_and_book, total_note_count, kinds_present, audit_attribution, compute_matrix_indexed, search, fts5_search, dashboard_stats) as `with _read_cursor() as conn: rows = conn.execute(...).fetchall()` — crucially fetching ALL rows inside the `with` so no lazy cursor escapes the lock. Because sqlite serialises in default threadsafety mode this is correct and the lock is held only for the (sub-ms, indexed) query. WorkCache (scripts/core/work_cache.py) already demonstrates this exact pattern (every get/put runs its execute inside self._lock) and is the reference implementation. Alternative if per-query locking is too coarse for audit_attribution/dashboard's full scans: switch each reader to open its OWN short-lived sqlite3.connect(_index_path()) (read-only, mode=ro) and close it in a finally — then there is no shared handle to close out from under anyone and _CACHED_CONN can be retired entirely. Either way the invariant is: no thread may call conn.execute on _CACHED_CONN while another thread can close it; today the lock guards only the close, leaving every execute exposed.
